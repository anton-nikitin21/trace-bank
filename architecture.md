# Архитектура и внедрение

## Реализовано в v0.1

HTML/JavaScript интерфейс и Python 3 standard library backend. JSON API, детерминированное извлечение реквизитов из текстового формата, правила комплектности, группировка по договору/ИНН, ссылки на строки исходного текста. Суммы внутри движка — целые копейки через Decimal; сравнение без float. SQLite хранит снимок входа, отчёт, хеш и запись проверки сотрудником. Сервер доступен только локально. Внешняя сеть для сценария не нужна.

Профиль supply-v1 находится в коде и версионируется. В промышленном варианте профили выделяются в конфигурацию, проходят утверждение владельцем и тестирование до активации. Профиль демо не претендует на достаточный набор документов по 115-ФЗ. Отсутствующий акт при авансе и разница договорной суммы с одним платежом не должны автоматически превращаться в замечания.

API: `GET /api/demo`, `/api/demo-fixed`, `/api/health`, `/api/history`, `/api/revision/{id}`; `POST /api/analyze`, `/api/economics`, `/api/approve`. Схема входа показана в JSON-примерах. Максимум 2 МБ на запрос, 300 операций и 300 документов. Нет API выполнения финансовой операции или отправки клиенту.

## Путь к банковской интеграции

Вход: идентификатор дела и структурированные пункты запроса из CRM/системы обработки; операции из согласованного адаптера; документы из внутреннего хранилища и OCR, если он уже есть. Движок получает только необходимые для выбранного профиля поля и ссылки на документ. Выход: карта требований/доказательств, пробелы, статусы ручной проверки и проект уточнения. Запись в CRM и отправка через ДБО выполняются после подтверждения сотрудником.

Не предполагаем существование открытого production API для банковских операций. Спецификации и права доступа согласуются с банком. Пилот сначала может использовать разрешённые выгрузки, затем read-only адаптер. Внедрение не требует замены системы риска или финмониторинга.

## Защита данных

Проектируем развёртывание on-prem с отключённым внешним egress, внутренним DNS, SSO через банковского провайдера, RBAC/ABAC и ограничением по очередям/делам. Между сервисами — TLS/mTLS по инфраструктуре банка. Шифрование в хранении и управление ключами — банковские средства; резервные копии тоже внутри контура. Уровень хранения персональных данных и меры определяет обследование банка. Сроки хранения задаются политикой процесса, не произвольным значением команды.

В журнале: субъект, версия требований, версия парсера/модели, хеш документа, результат, изменение сотрудника, время, ID корреляции. Журнал отправляется в защищённую систему аудита/SIEM с контролем изменения. Полные документы, клиентские реквизиты и тексты запросов не должны попадать в общие технические логи. Изоляция дел и авторизация проверяются на каждом API, а не только в интерфейсе.

Подлинность/электронная подпись — отдельный адаптер к согласованным средствам банка. Надпись «подписан» в OCR или ручных метаданных не означает криптографическую проверку. В демонстрации подписи явно не проверены.

Учитываем 152-ФЗ, 115-ФЗ, банковскую тайну и применимые требования ИБ как область совместного обследования, а не заявление о сертификации MVP. Банк и профильные специалисты утверждают юридически допустимые тексты, границы подсказок и необходимый уровень раскрытия причин запросов. Автоматическая оценка законности операций и обещание снятия ограничений не входят в продукт.

## Использование ИИ

В v0.1 нет зависимости от генеративной модели. Качество комплектности проверяется правилами и источниками. Для произвольных документов потребуется извлечение реквизитов через имеющийся в банке российский OCR/IDP либо локальный компонент, отобранный по отдельному тесту. Новые модели не добавляются без измеримого выигрыша относительно правил/существующего OCR.

Возможная LLM-функция — предложение классификации сложного требования или редактура проекта уточнения. Для неё нужен российский и/или on-prem runtime, структурированный ответ, ссылка на источник каждого утверждения, отказ при недостаточных данных и ручное подтверждение. Чужой текст документа считается данными: инструкции внутри документа не должны менять правила, запускать инструменты или расширять доступ. Тесты должны включать prompt injection, конфликтующие версии, отсутствующие поля и подмену реквизитов. LLM не формирует скрытый скоринг клиента.

## Масштабирование и надёжность

Прототип не предназначен для промышленной нагрузки. Целевая архитектура: stateless API, очередь обработки, независимые worker-процессы, PostgreSQL с партиционированием по требованиям объёма и защищённое объектное хранилище. Идемпотентность по ID дела, версии пакета и профиля; повторная обработка после сбоя не создаёт дубликат отправки. Внешние адаптеры имеют тайм-ауты, повтор с backoff и очередь ошибок. При недоступном OCR/реестре результат — «не проверено», а не «полный комплект».

Сначала измерить поток и размер файлов. После этого зафиксировать SLO по p95 времени для текстового пакета и по OCR отдельно, доступности, ошибкам и времени восстановления. Демо не даёт оснований обещать 99,99% доступности или обработку миллиона документов. Нагрузочный тест должен включать реальные распределения объёмов и повторные задания. Наблюдаемость: очередь, время стадий, отказ извлечения, доля ручной проверки, дрейф по профилям и инциденты доступа.

## Непокрытые случаи и ограничения

Произвольные PDF/сканы, граф отношений сложных договоров/переуступки, валюта/конвертация, изменения договора и юридическая эквивалентность актов требуют следующего профиля и данных. Платежи в текущем наборе трактуются как однонаправленные суммы; возвраты и сторно не поддерживаются, их нельзя автоматически включать как обычную оплату. Система не должна скрывать эти ограничения. Поддержка нового профиля начинается с эталонной разметки и отдельной оценки качества.
